The two carried-forward findings (`setuptools`, `msgpack`) remain accepted for the same reason
recorded since `v0.3.0-go-no-go.md`: both exist only as inert vendored artifacts inside `pip`'s own
bundle (`pip-*.dist-info/licenses/src/pip/_vendor/{setuptools,msgpack}`); `python -c 'import
setuptools'` / `import msgpack` both raise `ModuleNotFoundError` in the running image, and
`uvicorn app.main:app` never invokes either. No code or dependency change since `v0.4.1` reopens this.

**Owner risk acceptance — the 12 new HIGH/CRITICAL findings (`perl-base`, `libpcre2-8-0`,
`libsqlite3-0`, `gzip`):**

- **Root cause:** every one of these is a Debian point-release security patch for a package already
  present in the `python:3.14-slim` base image, at the *same* installed version this release has
  always shipped (e.g. `perl-base 5.40.1-6` → fixed `5.40.1-6+deb13u1` — a packaging patch, not a
  different upstream version). The Dockerfile, base image reference, `pyproject.toml`, and `uv.lock`
  have not changed since candidate freeze (confirmed via `git diff --stat` across I3.3-I3.6) or since
  `v0.4.1`'s own release. All 12 were newly disclosed in Trivy's vulnerability database between
  `v0.4.1`'s scan (`2026-09-10T20:46:18Z`, 3 results) and this scan (`2026-09-14T09:24:46Z`, 31
  results) — a live-database time-of-scan effect, not something this release's own code or dependency
  changes introduced.
- **Exploitability in this image:** `perl`, `gzip` (the CLI), and `libpcre2`/`libsqlite3` (as
  standalone attack surface) are pre-installed OS packages that ship with `python:3.14-slim`; none is
  invoked by AIP's own runtime code path. Verified directly: no `import sqlite3` anywhere in `app/`,
  no reference to `sqlite` in `uv.lock`, and no direct invocation of the `perl` or `gzip` binaries
  anywhere in `app/` (`grep` confirmed empty for all of the above). The running process is
  `uvicorn app.main:app`, a FastAPI/Neo4j-driver stack that does not exercise any of these libraries.
- **Decision:** repository owner reviewed this exact finding set and rationale and accepted it as
  `RISK_ACCEPTED` — not release-blocking for `v0.4.2`. Recorded here as the authorized-owner risk
  acceptance spec §11.4 requires; not a unilateral disposition.
- **Follow-up (non-blocking):** a future release should rebuild on a base image that has picked up
  these Debian point-release patches (or add an explicit `apt-get upgrade` step), which would very
  likely clear all 12 findings without any application-level change — noted as a known limitation
  below, not deferred silently.
