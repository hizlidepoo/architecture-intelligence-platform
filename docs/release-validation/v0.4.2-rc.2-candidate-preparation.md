# `v0.4.2-rc.2` Candidate Preparation — I3.2 re-freeze

## ⚠️ INVALIDATED

**This candidate (`6461db6d51ee29e9c973e62b005aa84d5d95c077`) is INVALIDATED.** I3.4's real VS Code
(GitHub Copilot Chat) actual-client qualification run found a second release-blocking transport
defect at this exact SHA: AIP's negotiated-mode guard hard-rejected any markerless follow-up request
missing an `MCP-Protocol-Version` header. The MCP specification's client-side rule says a client MUST
include this header on every follow-up (so VS Code's own omission is not itself spec-conformant), but
the spec's *server-side* backward-compatibility clause separately says a server receiving no such
header SHOULD tolerate it, not reject — exactly the allowance the pinned SDK already implements as a
graceful fallback. AIP's guard honored neither the SDK's own precedent nor that server-side allowance.
VS Code's real MCP client omits this header on `notifications/initialized`, so this candidate could
not accept a VS Code connection at all regardless of whose spec obligation was technically at issue.
Full finding, root-cause isolation, and sanitized reproduction:
[`docs/release-validation/v0.4.2-client-traces/vscode.md`](v0.4.2-client-traces/vscode.md).
Fix: [ADR 0014's second "Amendment" section](../adr/0014-negotiated-mcp-client-interoperability.md).

Per spec §4.4, a fix to `app/mcp/guard.py` ("MCP transport implementation") is a candidate-affecting
change: the technical GO this record would otherwise support is invalid, and a new
`RELEASE_CANDIDATE_SHA` must be frozen and requalified before this candidate's own automated gate
results below may be relied on again. Everything below this notice describes the *invalidated*
candidate and is retained as historical record, not as current release evidence.
